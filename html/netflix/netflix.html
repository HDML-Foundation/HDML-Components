Netflix — structural profile

Two tables, 6 137 titles and 81 355 credits, joined by a key that actually holds. The third dataset in this set and the first whose tables need no apology — every problem it has is inside a column.

1 The catalog you already have

There is no netflix connection, and you do not need one to start. The tenant's single tenant-a_maang connection points at jdbc:postgresql://localhost:5432/postgres — the whole database, not one schema — and Trino's PostgreSQL connector exposes every schema in it: 

show schemas from "tenant-a_maang"
  → airbnb, information_schema, maang, netflix,
     pg_catalog, public, spotify

So every identifier on this page reads `tenant-a_maang`.`netflix`.`titles`: the right schema through a catalog named after a different one. It works, and it will mislead the next person who reads it. The fix is a second hdml-connection named tenant-a_netflix against the same JDBC URL — the connection name is the Trino catalog name, and the tenant prefix is what satisfies the access rule tenant-a_.*. Nothing else changes.

2 Two tables, and the key holds

titles is 6 137 rows, one per film or series. credits is 81 355 rows, one per person-in-a-title. They join on id, and unlike the other two schemas in this set the join is sound in the direction that matters:

CheckRowsReading
titles.id distinct6 137 / 6 137a real primary key
credits with no title0referential integrity holds
titles with no credits3495.7% — inner join silently drops them
titles.title distinct6 089 / 6 137not a key — 48 collisions

The last row is the trap. title looks like an identifier and reads like one in a report, but 48 titles are shared by two different works — remakes, and a film and its documentary. Group by title and you silently merge them. Group by id.

Use a left join from titles to credits. An inner join is a filter that removes 349 titles, and nothing in the result says so.

4 Every column is text

All fifteen columns of titles and all five of credits are Postgres text. The CSV was loaded without a type declaration, so release_year, runtime, imdb_score and the rest are strings that happen to look numeric.

That is recoverable — every one of them parses. Checked against Trino, the count of non-null values where try_cast returns NULL is zero, for all five numeric columns. There is no dirty data hiding in the text; there is only a missing schema.

seasons is stored as 1.0, not 1. cast(seasons as integer) fails on every row. You need cast(cast(seasons as double) as integer).

This is a pandas artifact, and an instructive one. A column with any missing value becomes a float in a DataFrame, because the integer types have no NaN; write that back out and every value carries a .0 it never had. The airbnb schema has the same wound in person_capacity. Here it is worse, because seasons is missing for every MOVIE by design — so the one column guaranteed to have nulls is the one guaranteed to be mistyped.

5 Two columns that are really lists

genres and production_countries hold Python list literals inside a text column: 

genres                                  production_countries
['documentation']                       ['US']
['drama', 'sport']                      ['US']
['crime', 'drama', 'comedy', 'music']   ['US']

Not JSON — single quotes, and a space after each comma. 1 712 distinct genre strings and 438 distinct country strings, which is what a combinatorial explosion of a small vocabulary looks like: the real vocabularies are 19 genres and 107 countries. Any group by genres gives you 1 712 groups, all but a few of them size 1, and none of them a genre.

Unnesting is three string operations and a cross join: 

cross join unnest(
  split(replace(replace(genres,'[',''),']',''), ',')
) as t(e)
where genres <> '[]'
-- then: trim(both '''' from trim(e))

Strip the brackets, split on the comma, trim the whitespace, then trim the quotes — in that order, because the quotes sit inside the spaces. The where matters: 57 titles have [] for genres and 176 for countries, and without the guard each contributes one row with an empty-string genre that sorts to the top of every chart.

A title carries 2.57 genres on average, so the bars sum to 15 614 across 6 080 titles, not to 6 137. Treat them as tags, never as a partition — the one mistake this shape invites.

6 Columns that exist for half the rows

Two columns are conditional on another column's value, and both are exactly conditional — there is not a single exception in either:

ColumnPopulated whenNullRows in the other class
titles.seasons type = 'SHOW' 3 831 3 831 movies
credits.character role = 'ACTOR' 4 785 empty 4 785 directors

seasons is null for 3 831 rows and there are 3 831 movies. The null count is not approximately the movie count — it is the movie count.

That makes both columns safe to reason about, which is the useful half of the finding: a null in seasons carries no information beyond type, so imputing it, warning about it, or reporting it as missing data are all wrong. It is a subtype attribute in a flat table.

character is empty for another 6 038 ACTOR rows, which is ordinary missing data. Uncredited roles, voice work, archive footage. 7.9% of acting credits.

7 One column, two vocabularies

age_certification has twelve values, and they come from two different rating systems that never appear on the same kind of title.

1 348 movies carry an MPA rating (G/PG/PG-13/R/NC-17) and zero shows do. 2 046 shows carry a TV rating (TV-Y through TV-MA) and zero movies do. The split is total.

So this is two columns sharing a name, and the twelve-value vocabulary is a fiction — no title could ever take more than one of the two halves. An ordinal encoding over all twelve is meaningless: PG-13 and TV-14 are the same restrictiveness expressed in incompatible alphabets, and sorting them together interleaves two scales that were never comparable.

The honest model is a derived audience column that maps both alphabets onto one ordered set — all ages → older children → teen → adult — with the original kept beside it. What you must not do is let a chart sort the raw twelve.

2 743 titles (44.7%) have no certification at all: 2 483 movies and 260 shows. Absent, not unrated — NC-17 exists in the data, eleven times.

The pattern is worth naming. Every structural property that a database is responsible for — keys, referential integrity, null encoding — is sound. Every property that a loader is responsible for — types, formats, list flattening — is not. This schema was exported from a DataFrame and never re-typed, and all four of its defects are the fingerprint of that one decision.

9 The model this argues for

Three tables where the CSV gives two, and the casts pushed down into the model so no frame ever repeats them: 

tenant-a_netflix            -- its own connection, same JDBC URL

netflix_title               -- one row per work
  id, title, type
  release_year   integer
  runtime        integer
  seasons        integer    -- cast(cast(… as double) as integer)
  certification  varchar    -- the raw value
  audience       varchar    -- derived, one ordered vocabulary
  imdb_score, imdb_votes, tmdb_score, tmdb_popularity  double

netflix_title_genre         -- unnested, one row per (id, genre)
  id, genre

netflix_title_country       -- unnested, one row per (id, country)
  id, country

netflix_credit              -- as-is, left joined
  person_id, id, name, character, role

The two unnest tables are the substantive change. They turn a string-matching problem into a join, which is the difference between genres like '%drama%' — which also matches nothing else today, but only by luck, and would match a future psychodrama — and an equality predicate that is correct by construction.

Everything above is reachable today through `tenant-a_maang`.`netflix`, at the cost of writing the casts and the unnest in every frame. The model is what stops that repetition, not what makes the data reachable.
