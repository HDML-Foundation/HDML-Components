Spotify — structural profile

Two tables, a hundred rows each: the hundred most-streamed songs on Spotify, and their audio features. The smallest schema in this set, with no nulls anywhere — and the only one joined by a song title, because there is nothing else to join on.

1 The catalog you already have

There is no spotify connection, and you do not need one to start. The tenant's single tenant-a_maang connection points at jdbc:postgresql://localhost:5432/postgres — the whole database, not one schema — and Trino's PostgreSQL connector exposes every schema in it: 

show schemas from "tenant-a_maang"
  → airbnb, information_schema, maang, netflix,
     pg_catalog, public, spotify

So every identifier on this page reads `tenant-a_maang`.`spotify`.`features`. It works, and it will mislead the next person who reads it. The fix is a second hdml-connection named tenant-a_spotify against the same JDBC URL — the connection name is the Trino catalog name, and the tenant prefix is what satisfies the access rule tenant-a_.*.

2 Two tables, joined by a song title

features holds an audio-feature vector per song. streams holds the artist, the stream count and the release date. They describe the same hundred songs and they share no identifier column: features has id and name; streams has song and artist.

So the only available join is features.name = streams.song, and it does work — all 100 rows match exactly, with no trimming, casing or fuzzy matching. That is luck, not design. Both files were cut from one source in one order, and the titles were never edited afterwards.

A hundred-row title join that happens to be perfect is still a title join. Add one song whose name differs by an apostrophe between the two files and it fails silently, dropping a row from an inner join with nothing to indicate it.

3 The column that looks like a key

features.id is a genuine Spotify track ID — 22 characters of base62, the identifier the platform itself uses. It is the obvious primary key. It is not unique.

id has 99 distinct values across 100 rows. name has 100. The column that should be the key is the one that collides.

The collision is worth reading in full, because it is not a duplicate row — it is one song carrying another song's data:

TitleArtistid durationenergy tempo

SugarMaroon 5 6UelLqGlWMcVH1E5c4H7lY 2.900.81695.39

All twelve feature columns are identical between the two rows, not just the three shown — checked column by column, every one has a distinct count of 1 across the pair. And this is the only repeated feature vector in the table: group all 100 rows by the full twelve-column vector and exactly one group has more than one member.

That makes the diagnosis safe without leaving the data. Two different songs by two different artists cannot independently agree to four decimal places on twelve measurements. One row was populated from the other, and the shared substring Sugar says how: whoever built this dataset matched titles by containment, and Sugar matched Watermelon Sugar first.

One row in a hundred is another song's audio. Every statistic on the sibling report page is computed over 100 rows of which 99 are trustworthy, and nothing in the schema says which.

4 Fourteen columns, and four of them lie

Every column in both tables is Postgres text, as in the netflix schema. Unlike that schema there are no nulls at all — 18 columns across two tables, not one missing value — so the only thing a loader has cost you here is type information.

That matters more than usual, because the eleven numeric columns of features are on eleven different scales and nothing in the data says so. Seven really are the unit interval:

The other four are not on that axis, deliberately — putting them there is the mistake this section exists to prevent:

ColumnActuallyRangeWhat goes wrong
keyPitch class, categorical 0 – 11 Averaging it is meaningless. Its mean, 5.34, is not a key
modeBoolean — 1 major, 0 minor 0 – 1 Looks unit-scaled. Its mean, 0.65, is a proportion, not a level

key and mode are categorical integers sitting in the middle of eleven continuous ones, and only the column name distinguishes them. A generic "chart every numeric column" pass produces a mean key of 5.34 and reports it as data.

5 duration is not minutes and seconds

duration reads 3.33, 3.90, 5.91. That looks like minutes.seconds, and it is not — it is decimal minutes. The difference is 13 seconds on the first of those, and the data proves it without leaving the table:

37 of 100 rows have a fractional part greater than .59. No mm.ss encoding can produce .60 through .99, because there is no sixtieth second.

So 3.33 is 3 minutes 20 seconds, not 3 minutes 33, and the conversion to seconds is duration * 60 — not floor(duration)*60 + frac(duration)*100, which is what the column's appearance invites. Read the wrong way, every song in the table gains up to 39 seconds.

One value is worth a second look regardless: Don't Stop Me Now at 7.05 minutes is the table's maximum and 1.9× its mean, with the next longest at 5.91. Nothing inside the data can settle whether that is a long edit or an error, which is exactly why it is flagged and not dropped.

6 release_date has no century

Dates arrive as 29-Nov-19 — day, abbreviated month, two-digit year. They parse cleanly with date_parse(release_date, '%d-%b-%y'), all 100 of them, and the result spans 1975-10-31 to 2022-04-01.

The parse is correct here and it is correct by luck. A two-digit year is resolved by a pivot rule, and this table happens to contain nothing between 23 and 74 — the years are 75, 79, 91, 95 and then 00 through 22. Add a song from 1968 and 68 lands wherever the engine's pivot puts it, silently.

The column is also a text column that sorts alphabetically. 01-Apr-22 sorts before 29-Nov-19. Any ordering, range filter or min/max on the raw column is wrong, and wrong in a way that still returns rows.

The pattern from the netflix schema holds again, and harder. What a database owes you — completeness, parseability, internal consistency of ranges — is immaculate. What a loader owes you — types, units, a key, one row per thing — is absent. The difference here is that the missing key is not cosmetic: it is what let a wrong row through undetected.

8 The model this argues for

tenant-a_spotify            -- its own connection, same JDBC URL

spotify_song                -- one row per song, the two files joined
  name           varchar    -- the de facto key, until a real one exists
  track_id       varchar    -- NOT unique; keep, never key on it
  artist         varchar
  streams_bn     double
  released       date       -- date_parse(release_date, '%d-%b-%y')
  duration_sec   double     -- duration * 60, named for its unit
  key_pc         integer    -- pitch class 0-11, categorical
  key_name       varchar    -- derived: C, C#, D, …
  is_major       boolean    -- mode = 1
  loudness_db    double
  tempo_bpm      double
  danceability, energy, valence, acousticness,
  liveness, speechiness, instrumentalness  double   -- the unit seven

  suspect        boolean    -- true where track_id is not unique

Three of those columns are the whole argument. duration_sec carries its unit in its name, so the mm.ss misreading cannot be made twice. key_pc and is_major separate the two categorical columns from the nine continuous ones, so a chart-everything pass cannot average a pitch class. And suspect makes section 3's finding queryable instead of a footnote — one row is wrong, and a model that knows which one is the difference between a caveat and a filter.

Everything above is reachable today through `tenant-a_maang`.`spotify`, at the cost of writing the join, the casts and the date parse in every frame.
