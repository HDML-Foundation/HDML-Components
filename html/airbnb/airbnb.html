Airbnb — structural profile

Twenty tables, 51 707 rows, twenty columns, and not one of them typed. What is in the airbnb schema, measured against the running Trino — and the hdml-model those measurements argue for, which is not the shape the MAANG schema wanted.

1 The catalog you already have

No new connection is needed. tenant-a_maang points at the whole postgres database, and Trino maps every Postgres schema to a Trino schema — so `tenant-a_maang`.`airbnb`.`london_weekdays` resolves today.

Asked directly, that catalog answers with seven schemas — airbnb, maang, netflix, spotify, plus information_schema, pg_catalog and public. An HDML connection is a database, not a schema, and the name tenant-a_maang only ever described one of the things inside it.

That is workable and misleading in equal measure, so the recommendation is to declare a second connection — tenant-a_airbnb, same JDBC URL, same credentials — purely so the catalog name tells the truth and access rules can be written per dataset. It costs one hdml-connection and a compile. Until then every identifier on this page carries the maang name over airbnb data, which is exactly the confusion worth removing.

Adding it is not free of risk: a connection element compiles to find-drop-create catalog DDL, so declare the new name and leave tenant-a_maang untouched.

2 Twenty tables, and the keys are in the names

city and period exist nowhere in the data. They are encoded in the table names — london_weekdays, rome_weekends — so every model over this schema has to promote them to columns before anything can group by them.

Ten cities × two periods, identical twenty-column layout in all twenty tables. That uniformity is what makes one model over the whole schema reasonable; the naming convention is what makes it a union rather than a join. London and Rome carry a fifth of the corpus between them; Amsterdam is the smallest at 2 080 rows.

col_0 is not a key. It is a per-file row index restarting at 0 in every table: 51 707 rows carry only 5 379 distinct values.

Unique within a table, worthless across the union. The real identity of a row is (city, period, col_0) — and two thirds of that tuple has to be manufactured from the table name first. No column, and no combination of columns present in the data, is a primary key.

4 Cardinality: dimensions, measures, and one impostor

Distinct values per column across all 51 707 rows, log scale. Three bands, and each one is a modelling instruction.

At the bottom, the dimensions: two-valued flags and booleans, three room types, nine cleanliness ratings, ten bedroom counts. Group by these freely. At the top, four columns —dist, metro_dist, attr_index, rest_index — with 51 707 distinct values, one per row: continuous measures, and collectively the closest thing this schema has to a natural key. In between sits realsum at 10 497 and the coordinates at ~21–24 000, lower than the indices because listings share buildings.

The impostor is person_capacity at ten distinct values for five real capacities — §5. The marks are points, not bars, because a bar's simple y form desugars to a baseline of zero and zero has no position on a log axis.

Twenty category labels will not fit under a 760 px axis, so this figure omits its x labels rather than overprinting them; read the order off the dictionary in section 3, which is the same pos the frame sorts by.

5 The same number, stored two ways

person_capacity holds '2' in 757 rows and '2.0' in 23 576 — the same capacity, two strings. Grouping by the raw column splits every capacity in two.

This is the single most damaging thing in the schema, because it fails quietly. A GROUP BY person_capacity returns ten groups where there are five real ones; a filter on '2' silently misses 23 576 rows; and cast(person_capacity as integer) does not merely round — it throws, because Trino cannot cast the string '2.0' to INT. The route is cast(cast(… as double) as integer), and the model in section 8 does exactly that.

Both forms appear in every capacity, in roughly the same ratio — so it is not one bad city or one bad file, and no filter isolates it. The only fix is to normalise on read.

6 Value ranges

Observed minimum to maximum, pooled across all twenty tables, log scale. realsum spans three decades — €34.78 to €18 545.45 — which is the heavy tail every price model on this data has to decide what to do about. The two *_index_norm columns confirm they really are normalised to 100; the raw indices are not, running to 4 514 and 6 696.

Five columns are deliberately absent, and their absence is the figure working rather than failing: col_0, multi, biz and bedrooms all have a minimum of zero, and lng goes negative to −9.23. Neither has a position on a logarithmic axis, so the model returns NULL endpoints for them and the mark is simply not drawn — missing rendering as absent rather than as zero.

8 The model this argues for

An HDML model joins its tables — there is no union in the model vocabulary. So a twenty-table stack has exactly one expression: a single type="query" table that unions them and promotes the partition keys.

This is the opposite conclusion from the MAANG schema, where five type="table" entries joined on a shared key were the right shape. Here every table has the same columns and no shared key at all; stacking is the only meaningful composition, and the city and the period have to be manufactured on the way through: 

<hdml-model name="airbnb">
  <hdml-table name="listing" type="query" identifier="
    select 'amsterdam' as city, 'weekdays' as period, *
      from `tenant-a_airbnb`.`airbnb`.`amsterdam_weekdays`
    union all
    select 'amsterdam', 'weekends', *
      from `tenant-a_airbnb`.`airbnb`.`amsterdam_weekends`
    union all
    ... eighteen more ...">

    <!-- promoted from the table names -->
    <hdml-field name="city"   type="utf-8"></hdml-field>
    <hdml-field name="period" type="utf-8"></hdml-field>

    <!-- '2' and '2.0' are the same capacity: normalise here,
         once, or every consumer re-learns it the hard way -->
    <hdml-field name="person_capacity" type="int-8"
      clause="cast(cast(`person_capacity` as double) as integer)">
    </hdml-field>

    <hdml-field name="realsum"   type="float-64"></hdml-field>
    <hdml-field name="room_type" type="utf-8"></hdml-field>
    <hdml-field name="bedrooms"  type="int-8"></hdml-field>
    <hdml-field name="dist"      type="float-64"></hdml-field>
    <hdml-field name="lat"       type="float-64"></hdml-field>
    <hdml-field name="lng"       type="float-64"></hdml-field>

    <!-- booleans have no type: keep the string, or fold it -->
    <hdml-field name="superhost" type="int-8"
      clause="case when `host_is_superhost` = 'True'
                   then 1 else 0 end">
    </hdml-field>
  </hdml-table>
</hdml-model>

Three consequences to plan for. Fields surface downstream as {table}_{field}, so a frame over this model reads listing_realsum — name the table for what a row is, because that prefix is permanent. There is no date anywhere in the schema, so nothing here is a time series: period is a two-valued category, not a calendar. And a model is the right place for the capacity normalisation precisely because it is the layer every consumer shares — pushed into a frame it gets rewritten, differently, by whoever writes the next one.

Not measured here: on-disk size. Trino's PostgreSQL connector exposes no relation-size statistic, so byte counts need a direct Postgres session. Row counts and cardinalities are the size proxies this page can honestly report.
