# HDML-Components

Lit-based **TypeScript web components** that let an author declare an HDML document in plain
HTML — `<hdml-connection>`, `<hdml-model>`, `<hdml-frame>`, etc. — and a sibling `<hdml-io>`
component that serializes that DOM to FlatBuffers (via `@hdml/*` libraries running in a Web
Worker) and uploads it to an HDIO server. Published to npm as **`@hdml/components`**
(Apache-2.0). Built with Lit 3 + `@web/dev-server` + `@web/test-runner` (Playwright,
chromium/firefox/webkit). Ships **four artifacts** from one source tree: `cjs/`, `esm/`,
`dts/`, and a minified IIFE `bin/index.min.js` (worker inlined as a string).

npm run build              # clear + lint + test + compile_all + typedoc → docs/

[`properties.ts`](src/hdvl/properties.ts) holds SPEC §9's 35-property registry. **All twenty-one elements have bodies** ([`view.ts`](src/hdvl/view.ts), the two `plane-*.ts`, [`fallback.ts`](src/hdvl/fallback.ts), the three `scale-*.ts`, [`mark-line.ts`](src/hdvl/mark-line.ts) + [`mark-rule.ts`](src/hdvl/mark-rule.ts) since step 20, [`mark-area.ts`](src/hdvl/mark-area.ts) + [`mark-bar.ts`](src/hdvl/mark-bar.ts) since step 21, [`mark-point.ts`](src/hdvl/mark-point.ts) + [`mark-arc.ts`](src/hdvl/mark-arc.ts) since step 22 — **all six §6.1 marks paint** — [`guide-axis.ts`](src/hdvl/guide-axis.ts) + [`guide-grid.ts`](src/hdvl/guide-grid.ts) since step 23, and [`guide-tick.ts`](src/hdvl/guide-tick.ts) + [`guide-label.ts`](src/hdvl/guide-label.ts) since step 24, [`layout-pie.ts`](src/hdvl/layout-pie.ts) since step 27 — **four of the five guides paint, under both planes** — and [`container-stack.ts`](src/hdvl/container-stack.ts) + [`container-cluster.ts`](src/hdvl/container-cluster.ts) since step 29, **both layout containers**, and [`guide-legend.ts`](src/hdvl/guide-legend.ts) since step 31 — **all twenty-one elements have bodies, and no tag is "registered but inert"**). **All twenty-one `HdvlElement` subclasses declare `scene(ctx)`** — Contract 1 is not merely complete but **implemented** — and **eight of them return `null`**, which §2.3 makes a contract-complete answer; all eight (view, both planes, three scales, both containers) return `null` permanently, because those families emit no group at all — for a **container** that `null` is now its per-frame hook, exactly as a scale's is: `scene(ctx)` is where it derives and publishes what its children read — for a scale that `null` is also its **per-frame hook**: `scene(ctx)` is where it resolves its `Scale`, which is why a scale with no widgets under it still reports a domain and still fires `hdml-scale-change`. **Contract 2 is [`scale.ts`](src/hdvl/scale.ts)**, one implementation shared by all three scale tags, because they differ in exactly three things — the kind, which attributes they publish, and which modifiers V18 lets them carry — and splitting §4.2's step order three ways would be three chances to disagree about it. It owns §4.2's seven-step domain resolution (which **never reads a pixel**: `nice`'s step comes from the domain and its own count, so a resize cannot move the data) — and since step 25 `nice` rounds to **the scale's own ladder**, not always the linear one: SPEC §6 names only the datetime case, and reading the silence about `log`/`pow`/`symlog` as *linear* widened a delivered `[12.5, 1250]` to `[0, 1400]`, which V2 errors on and which projects nothing (corpus `05-scatter` B, the first page to run it; approved under D1). `log` rounds to the enclosing power of the base, symlog per endpoint by region, and `linear`/`pow`/`sqrt` are unchanged because §4.8's pow ladder **is** the numeric one. It also owns SPEC §7's explicit `step=`, whose multiples are generated over an integer index range — `i / divisor` where the step has an integer reciprocal — because `0.35 / 0.05` is `6.999999999999999` and the obvious predicate silently drops a domain's last tick, §4.3's ranges from each scale's own **content box**, the `Binder` that makes a `values` column an ordinary `raw:false` subscription, `paint()`, and the `hdml-scale-change` edge; every number in it comes from `kernel/`, so it contains no ladder, no band formula, no transform and no formatter of its own. It reaches `../hdio/delivery` `type`-only, as `subscribe.ts` does — those two are the whole of `src/hdvl/`'s reach into that module, and `ColumnType` is derived from `Delivery` rather than imported because `check-dist.mjs` forbids `../hdio/decode` outright. **The marks project through one seam**: [`mark.ts`](src/hdvl/mark.ts) is the mark base — `Projection`, and everything else every mark widget shares. **A mark never names a channel**: it reads `Projection.channels`, which is the *plane's* answer (`x`/`y` under a cartesian plane, `angle`/`radius` under a polar one), and a plane supplies its own projection through the duck-typed `ProjectionSource` — so the polar implementation landed in [`plane-polar.ts`](src/hdvl/plane-polar.ts) at step 22 and **no widget gained a branch** (H7) — the prediction held on contact, and adding it changed that one file. **Measured a second time at step 26**, when `hdml-line`, `hdml-area` and `hdml-point` first ran under a polar plane: a **zero-line** diff to all three, with [`mark-polar.test.ts`](src/hdvl/mark-polar.test.ts) as the evidence — a claim of this shape can only be proved by fixtures that pass against files nobody touched. The one polar-scoped thing a shared mark carries is `hdml-line`'s `closed`, SPEC §7's radar loop: a boolean attribute that sets the `path` node's `closed` flag (a `Z` per subpath, **no repeated vertex**), scoped by the plane's *channels* and therefore **inert on a cartesian plane**, where the emitted node is byte-identical to one written without it. `hdml-area` publishes the same attribute behind the **same predicate** (`closedOf`, shared, R12) and does something different with it: its regions already close, so on a flat plane it is inert and the node is byte-identical without it, while under a polar plane it splits each region into **two subpaths** — an outer ring and an inner one — instead of one cap-joined outline that closes *through the pole* and notches `10-radar`'s band. The two are **already counter-wound** (the lower edge is emitted reversed), so the default `nonzero` rule punches the hole: no fill rule is authored, nothing is added to §2.5 and the renderer is untouched. Decided with the user at step 27 after step 26 raised it; SPEC §7 carries the dated amendment. Its **pole** is §4.6's: the centre of the radius-channel scale's content box, or the plane's where no radius scale exists, read off the MEASURE snapshot and resolved per widget, because the widget's own chain says which radius scale serves it. **And so is its radial range** — SPEC §3 states the two in one sentence, over one box, and step 22 implemented the fallback for the pole only. Step 28's corpus gate found it: a **pure pie chain** (`08` A–D, `12-B` — an angle scale and no radius scale at all) resolved no ceiling, so every sector and every angular guide bailed and five figures painted an **empty scene with no `:state(error)` and no diagnostic**. The correction is one member on `Projection` — `span(channel)`, a channel's range in its own unit, the scale's `range()` where one serves and **whatever the plane supplies** otherwise — and the four readers of *"the other channel's range"* (`hdml-arc`'s ceiling, `hdml-rule`'s span, `hdml-grid`'s crossing extent, `guideAcross`) now ask the plane instead of the scale, so there is one answer and not four (R12). `plane-polar.ts` resolves the **box** and derives both readings from it; a cartesian plane declines every channel, so `span("y")` with no y scale is `null` exactly as the inline spelling was, and the polar plane answers for its **second** channel only, since an angular range is `--hdml-angle-start`/`-end` on the angle scale. `createProjection` shares the chain lookup, §4.7's whole drop rule and the ordinal test between both planes, so the only thing a plane supplies is how two projected positions compose into a point — the identity pair for cartesian, `polarPoint` for polar. It also owns SPEC §5's first-character binding grammar (`slotValuesOf`: a column, a literal column, or a scalar broadcast), §5's **N**, `markBindings`, `datumOf`, §6.1's paint resolution in **both** halves (`strokePaint` for a stroked mark, `fillPaint` for a filled one — a filled mark does **not** also stroke, because §6.1 names no outline and SPEC §9 registers no property that would control one) and §6.2's parameter read — every one of them keyed by **slot** rather than by `x` and `y`. **And it owns H8's resolver**: `rangedValuesOf(el, channel)` returns a channel's values as a `(low, high)` pair, resolving §6.4's simple form into the ranged primitive (`y` ≡ `y0="0"`, polar `radius` ≡ `r0="0"`) **before any geometry exists**, with the sugar expressed as a synthetic *scalar* `SlotValues` byte-identical to what the literal spelling produces — so no code below it can tell which form the author wrote, and `RangedValues.sugar` exists only for a test to assert the desugaring happened. **Step 29 changes nothing inside `hdml-bar`/`hdml-area`**: `low` is an ordinary `SlotValues`, so a container builds `{slot, rows: N, scalar: false, at: (k) => baseline[k]}` over its own allocated array (§12 duty 4) and the resolver consults that per-frame override *before* it reads attributes; that override is the only thing the container slice adds. [`mark-line.ts`](src/hdvl/mark-line.ts) emits **one** stroked `path` for the whole series, `fill: null`, `i: -1`, with row identity in its per-vertex `i`; [`mark-rule.ts`](src/hdvl/mark-rule.ts) emits **one node per row**, each with a real `i`, spanning the *other* channel's `range()` (§4.3's, not its own box) — between them the two readings of §2.5's `i` field. [`mark-area.ts`](src/hdvl/mark-area.ts) emits **one filled `path`**, each contiguous stretch of rows a **closed** subpath: the upper edge forward, a line across, then the lower edge **reversed** — and the reversal happens *before* the curve, because `natural`'s solve is global over its run and `bezier` picks tangents per segment, so curve-then-reverse would put the lower edge off the data. [`mark-bar.ts`](src/hdvl/mark-bar.ts) emits **one `rect` per row** whose **orientation is derived, never authored** — the band-filling side is whichever channel resolves an *ordinal* scale, so the same markup with `x`/`y` swapped lays the bars down and there is no orientation attribute on the tag — and it is **one of the two widgets that read `bandOf().width`** — `hdml-arc`'s ordinal-angle slice is the other, since step 26: §4.4 gives a bar and an equal slice the band, and every other lookup, an area's vertex included, the `centre`. A row whose two ends are equal is a real datum and gets a **zero-extent** rect. A gap is a `Subpath` boundary and is **never bridged**: the mark splits its rows into runs and `kernel/curves.ts` curves each independently, and on an area a dropped row breaks **both** edges at once. [`mark-point.ts`](src/hdvl/mark-point.ts) emits **one `ellipse` per row** — or one `rect`, which is what `--hdml-tick-style`'s registered initial actually is, both centred on the projected point and sharing one extent. That extent is a **diameter** in both its forms, so an ellipse takes half of it: reading `--hdml-tick-width` as a radius draws every glyph at twice its declared size and no scene assertion catches it, which is why the test asserts against the *computed property*. A bound `size` supplies **both** extents (a circle — the channel is one number, and there is no second one to keep an aspect ratio against) and its ramp is the **scale's**: `--hdml-size-min`/`-max` are §4.3's range for the `size` channel, read once in `scale.ts` from the size scale's own box, so the widget calls `project()` and interpolates nothing (R12). [`mark-arc.ts`](src/hdvl/mark-arc.ts) emits **one parameterised `arc` per row** — `{cx, cy, r0, r1, a0, a1}`, never a pre-serialized path (§2.5) — with angles in **degrees** straight off the projection. Its three radial cases are not one rule: `r0`+`r1` bound is the author's, `radius` bound is sugar for `r1`, and **fully unbound is the full radius range**, the one case the ranged resolver cannot express (`null` is what it returns for an unbound channel) and the one that makes the pure `a0`/`a1` form interchangeable with `hdml-pie`. `--hdml-inner-radius` supplies the **synthetic** `r0` only — an authored one may paint inside the hole, because authored data is sacred — and `RangedValues.sugar` is read **there and nowhere else in the project**, as *did the author say anything about the lower edge* rather than as a geometry branch. Its **ordinal-`angle` equal-slices form** landed at step 26: a slice is §4.4's band, `a0 = bandOf().start` and `a1 = start + width`, so `--hdml-bandwidth` is what opens the gap between slices and a solid rose is one `--hdml-bandwidth: 1` declaration on the angle scale — approved under D1, and the reason `hdml-bar` is no longer the only `bandOf().width` reader. The band comes from `Scale.bandOf` and never from a `360 / n` of its own (R12), since the angular range is `--hdml-angle-start`/`-end` and need be neither a full turn nor ascending. [`layout-pie.ts`](src/hdvl/layout-pie.ts) is §6.3's **one cross-row layout widget**, and its geometry is `hdml-arc`'s *to the node*: `scene()` on both tags is one call to `mark-arc.ts`'s free `sectorScene`, which owns everything from the pole down, and the only thing the two differ in is the **angle form** each supplies — so there is exactly one `k: "arc"` node literal in the project and SPEC's claim that 08-A and 08-C are interchangeable is a property of the code rather than a promise about it (asserted by comparing the two scenes). The pie's form is §6.3's derive: cumulative **fractions**, so its angle scale is always the authored `min="0" max="1"`; a `null` is excluded from the total and takes no slice, so its neighbours stay adjacent and the turn still closes; a zero total is `:state(empty)`, not a full ring; a **negative** value is V7's error and paints nothing; row order is slice order and nothing sorts. `a1ₖ` is a **running quotient** `acc / total` rather than RFC §6.3's algebraically identical `a0ₖ + vₖ / total`, because only the first makes the last slice's high edge land *exactly* on the range's end. It publishes no radial attribute at all, so it always takes the arc's third radial case — the full range floored by `--hdml-inner-radius`, which is 08-B's widget-scoped doughnut and 08-D's plane-scoped ring alike — and §12 duty 4 is honoured by the prefix sum allocating its own array, asserted against the delivered buffer. **And the containers re-parameterise them without touching them**: [`container.ts`](src/hdvl/container.ts) is the layout half's seam — **two registries a container writes during COMPUTE and two readers consult**, so `hdml-bar` and `hdml-area` contain no container branch at all. `hdml-stack`'s is the **ranged override**, which `mark.ts`'s `rangedValuesOf` reads *before* it reads attributes: §6.4 makes the ranged form the primitive a container compiles into, so a stacked child is a plain ranged mark from `y0ₖ` to `y0ₖ + yₖ` and **`mark-bar.ts` gained not one line at step 29** — H8's prediction, measured, with the two forward references in that file deliberately left where they were written, because retiring them would change the file whose not changing is what they predict. `hdml-cluster`'s is the **band slot**, which `scale.ts`'s `chainScaleOf` applies: SPEC §7 calls the subdivision *"an anonymous inner band scale whose domain is the children in DOM order"*, so it is the **scale** a clustered widget resolves that differs and not the widget's arithmetic, and the inner band is `kernel/scale-band.ts` at **`b = 1`** rather than `outer.width / n` (**R19** — *"there is no authorable inner gap"*, and `b` is an ordinary parameter of the one band formula). Slot is the child index and slot count the **rendered**-child count, both structural — which is what retired the `--hdml-band-slot`/`-slots` pair, since no validator can check a cascade. Both containers also **hoist the shared channel** through the ranged override, because V6 forbids a child from binding it and a stacked bar therefore has no `x` to read; `04-grouped-stacked` E's two inner stacks bind nothing at all and take the cluster's. Entries are keyed by the **child** and fenced by `owner === child.parentElement`, so a child moved out of its container stops reading one on the next frame; and the ordering that makes the push safe is a property of the walk, not a new phase — `resolve.ts` lists a view's elements in **document order** and `schedule.ts` walks that list, so a container's `scene(ctx)` has always run before its children's. **`hidden` is the platform's** *(decided at step 29 — the tag surface left the question open at step 09)*: `HTMLElement.hidden`, read **once**, in `subscribe.ts`'s `paintSuppressed`, so every widget honours it and none spells it — two mechanisms could disagree, and a page that made a hidden series `display: block` would get a chart whose bands do not add up with nothing saying so. The field stays named `hiddenAttr` only because a `null | string` field of that name shadows the boolean IDL property. The one thing a container **cannot** express through a value override is **which element a property is read off**: SPEC §9's `--hdml-curve-*` rows make the reader the *stack* for a stacked area (§7: per-child curves would tear the shared edges), so `container.ts`'s `curveSourceOf` answers with one element and `mark-area.ts` — alone among the marks — gained a line for it. **And the guides sit beside the marks**: [`guide-spec.ts`](src/hdvl/guide-spec.ts) is the guide base — what §6.5's four positional guides share, which is everything before *what is repeated*. It owns `resolveGuide` (channel → plane → scale → the guide's own and the scale's measured boxes → §4.6's **pole**, when the plane composes about one), `tickSpecOf`, `guidePoint`, `guideLine`, `guideRing`, `guideEdge`, `guideAcross`, `guidePlacement` and `guideGroup` — and **step 24 imported it rather than reimplementing it, without needing it to grow a single member** — **H6 was measured at step 31 and this file has a zero-line diff**: `hdml-legend` reads exactly two of its members — `tickSpecOf`, so the three density attributes have one reader, and `guideGroup`, so a legend's group carries `role: "guide"` and the same five box-level fields — and calls `resolveGuide` not at all, because that function's contract is a channel the *plane* consumes and `color` is consumed by no plane. Two of those are the ones a later slice cannot re-derive: **`tickSpecOf` forwards `count`/`step`/`values` and resolves between them nowhere** — `Scale.ticks` and `thinOrdinal` already test `values`, then `step`, then `count`, and a second precedence here would be a second ladder entry point in all but name (R12); and **`guideEdge` derives *which edge of its own box faces the scale*** from the two measured boxes, because SPEC §7 gives placement to CSS and the tag no `position` attribute — §6.5 derives `hdml-label`'s anchor and baseline from that same fact at step 24. `guideGroup` is `markGroup`'s sibling and not a `role` parameter on it: §3.4.1 decides `empty` on **mark** nodes, so a chart of axes over no data must read as empty, and a parameter would let a mark pass `"guide"`. A guide node carries `i: -1` and **no vertices** — `i` is a source row and `vertices` are projected *data* vertices, and a guide has neither, so hit resolution can never land on a widget that implements no `datumAt`. [`guide-axis.ts`](src/hdvl/guide-axis.ts) emits **one stroked `path`** over its channel's `range()` (§4.3's, not its own box) crossing at that near edge; [`guide-grid.ts`](src/hdvl/guide-grid.ts) **one `path` per tick** across the *other* channel's range, at `scale.ticks(spec)`'s positions and never a ladder of its own — on an ordinal scale that is the band **centre**. [`guide-tick.ts`](src/hdvl/guide-tick.ts) emits **one `rect` or `ellipse` per tick**, `--hdml-tick-style`-shaped and centred on both axes, whose `--hdml-tick-width`/`-height` are **diameters** exactly as `hdml-point`'s are — and whose `decorative: true` lives in **the node kind it emits**, since §2.5 gives `decorative` to `text` alone and a tick emits none, which the test asserts directly. [`guide-label.ts`](src/hdvl/guide-label.ts) emits **one `text` per tick**, `decorative: false`, `font` transferred off the snapshot, whose `anchor`/`baseline` are **derived** — the sign of `edge − centre` on the perpendicular axis, so §6.5's four rows fall out of one predicate rather than four cases keyed on the channel, which is the authored `position` SPEC §7 forbids — and which does **not** call `ctx.measureText`, because a `text` node carries its own anchor and the renderer places it (flow is what needs the seam, and `hdml-legend` is its one caller since step 31 — an entry's line height is `max(swatch, ascent + descent)`, which no `text` node carries). Its formatting is §4.9's, in three cases with one implementation each: an **ordinal** channel renders domain strings verbatim, a **datetime** one goes through `Scale.format` because only the scale knows its `timeZone`, and a **continuous** one goes through `formatCompactSet` over the whole **set** — never per value, or one axis reads `900K, 1.2M, 1.5M`. The locale is `scale.ts`'s `localeOf`, **exported at step 24** so both paths resolve it identically at the **view** and one axis cannot format in two locales. **★ All four guides paint under both planes, through one code path** (step 27). This module used to carry a `readonly [Channel, Channel]` naming `x`/`y` and refuse every other plane outright — H7 half-applied, since the mark half had asked the plane since step 22 — and step 27 **deleted it**. `guidePoint` now hands both positions to `Projection.point` in the plane's own channel order, whose cartesian output is *unchanged* because that plane composes with the identity pair; `resolveGuide` resolves a `pole` as `projection.point(0, 0)`, the read `hdml-arc` already made; and the four elements read polar-ness back off `pole !== null` plus `first`, so **no guide element names a channel**. One name survives, `ANGULAR`, asked once here to decide whether a plane composes about a pole — the identical question `mark-line.ts`'s `closedOf` asks, a fact about *channels* and not a branch on plane kind. `guideAcross` is the units question the split turns on: a **view** coordinate is a legal `across` exactly when the other channel's range is measured in one, so a flat plane's guide reads its own box (`guideEdge`) and a polar one reads the other channel's range's **far end** — the rim, or the end of the turn, which on a full turn is the twelve-o'clock spoke. `guidePlacement` is `guide-label.ts`'s old `placementOf` generalised and moved up: **one predicate, the per-axis sign of the outward normal**, constant and axis-aligned under a flat plane (which is *why* §6.5's four rows each carry a `middle`) and radial under a polar one, with a magnitude-relative deadband because `cos(π / 2)` is `6.1e-17`. `guideRing` is the `arc` node an angular `hdml-axis` and a `--hdml-grid-shape: circle` grid both emit — `r0 === r1`, a zero-thickness annulus, which is what a stroked ring *is*. `--hdml-grid-shape` is [`guide-grid.ts`](src/hdvl/guide-grid.ts)'s alone and is consulted only on a radial guide under a pole: `circle` is that ring per tick, `polygon` a closed `path` through the **angle scale's** `ticks({})` positions — *the scale's*, because `10-radar` writes `count="5"` over six categories and a polygon built from the grid's own spec would have five sides. **★ And [`guide-legend.ts`](src/hdvl/guide-legend.ts) is the last element in the vocabulary** (step 31) — the **visual-channel** guide, whose two modes are **derived from the resolved scale's tag** and never authored: an **ordinal** scale gives a key of one swatch-plus-name entry per domain value, **always the whole domain** (*"a thinned key lies"*, which is why the density attributes are V20's error there rather than being quietly ignored), and a **continuous** one gives a ramp bar plus formatted values at `ticks(spec)`. It reads `Scale.domain()` and not the marks, so a category no row uses still gets its entry (§6: a scale is never fed by widgets) and a page with no data provider at all still renders one — it declares **no `bindings()`** and `subscribe.ts` never sees it. **One entry is one datum of a mapping**: the swatch and the name are generated together, from one value, in one loop, so entry *k*'s colour **is** `paint(domain[k])` and its text **is** `domain[k]` by construction — which is finding 17's whole reason for a dedicated element, since the `hdml-tick` + `hdml-label` spelling made swatch↔name alignment **cascade-determined geometry no validator can check** and the `hdml-axis channel="color"` spelling needed **modal attribute sets**. The swatch's `decorative` lives in **the node kind it emits**, exactly as `hdml-tick`'s does, and the name is real `text` with `decorative: false`. **R18 measured**: every ramp sample is a `Scale.paint(v)` call at a real domain value, so a `hdml-point` bound to the same scale returns the same string byte for byte, and this file interpolates no colour at all. The bar's **axis is the ramp fraction** — which is what made step 31 change `scale.ts`: `range()` stays `null` for `color` (a colour's range is a palette) but `project()` returning `null` beside it made `ticksFor` drop every tick it generated, so `ticks()` answered `[]` on **every** colour scale and a continuous legend would have had no graduations at all, silently. On a *continuous* colour channel `project(v)` is now the ramp fraction in `[0, 1]` — the number `paint()` already maps through — and `Tick.at` is that fraction, so bar and graduations share one axis and a `log` colour scale's colours sit where its values sit; the ordinal colour case stays `null`, because a palette slot is not a position. Its samples are taken uniformly in the **domain**, because Contract 2 publishes no inverse and a second one here is what R12 forbids. Its three `--hdml-legend-*` properties are one axis question asked once (`direction` is the entry flow **and** the bar's orientation; `gap` is the swatch↔name gap **and** the entry gap; `swatch-size` is the swatch's extent **and** the bar's thickness, and is **not** `--hdml-tick-width`, which SPEC §9 gives to `hdml-tick`/`hdml-point` alone). §4.9's formatting is **`hdml-label`'s** — `textsOf`, exported at step 31 for its second caller, so the shared compact prefix over a *set* has one implementation and `guide-spec.ts` did not have to grow to hold it. **Overflow clips and v1 builds no scrollport**, and nothing in the element implements either: `guideGroup` transfers `Measured.clip` and the renderer clips the group to its box, so `auto`/`scroll` clip without a scrollbar because the entries paint on the **view's** surface and this element's own box has nothing of its own to scroll. **The frame sits beside them**: [`resolve.ts`](src/hdvl/resolve.ts) is the resolution index — one rect-free depth-first walk per structural change answering view / plane / scale-chain / tip / container / error-unit / effective-`source`, plus `byUid`, and **the only place that knows how an element finds its view** (`HdvlElement.view` is a read of it; ## External contracts

This repo *promises* the following to its consumers; any change here is a cross-repo change.

- **Custom-element registry** — the `.` root entry registers exactly **12** `hdml-*` tag names at module-load time and that number is frozen (R11); the `./hdvl` entry registers **21 more**, the whole display vocabulary, in one commit that never moves again. All tag names are defined in [`@hdml/types`](https://www.npmjs.com/package/@hdml/types) as `HDML_TAG_NAMES` (33 = 12 data + 21 display). Importing `@hdml/components` has side effects; importing `@hdml/components/hdvl` additionally registers SPEC §9's 35 `--hdml-*` custom properties and adopts the fallback rules into `document.adoptedStyleSheets`. See [docs/components.md](docs/components.md).
- **`HDML.supports(tag[, attr])`** — importing `@hdml/components/hdvl` registers a `supports` function on `globalThis.HDML`, **additively** (the namespace object is reused, never replaced, so a page loading two builds or a host app owning `window.HDML` keeps everything else on it). It is **registration-based**: `true` iff this build registered that display tag, and — with a second argument — iff the attribute is in that tag's published `*_ATTRS_LIST`. A page that never imports the `./hdvl` entry gets `false` for all 21. See [docs/decisions.md](docs/decisions.md).
- **`HdmlPointerEvent`** — the display half proxies `pointermove` / `pointerdown` / `pointerup` / `pointercancel` from the widget under the cursor. The proxied event **extends `PointerEvent`** (so `e instanceof PointerEvent` holds and every pointer field survives) and carries `index` and `datum` as **own properties, not `detail`** — `UIEvent.detail` is a `long` and coerces an object to `0` on all three engines. It is `bubbles` + `composed`, dispatched **from the widget** (so series identity is the event target — there is no `series` field), and the native event is **not** stopped: a host app sees both and tells them apart by class. The four named `hdml-*` events (`hdml-data`, `hdml-scale-change`, `hdml-render`, `hdml-error`) stay `CustomEvent`s carrying `detail`, and are all dispatched **after PAINT** from a queue collected during the frame. See [docs/architecture.md](docs/architecture.md).
- **`hdom-changed` DOM event** — every HDQL element dispatches a non-bubbling `CustomEvent<HdqlElement>` on `document` whenever it is connected, disconnected, or has an observed attribute change. `<hdml-io>` is the canonical listener. See [docs/architecture.md](docs/architecture.md).
- **D8 discovery bus** — three `document` events (`bubbles`/`composed`, names configurable via `window.HDML_CONFIG`) are how a data-binding consumer talks to `<hdml-io>`. The seam is an event plus a callback, so **any** consumer can implement it — that is what makes `FakeIo` and the conformance suite possible — and the **first** one is [`src/hdvl/subscribe.ts`](src/hdvl/subscribe.ts), in this package. It dispatches **`hdml-io-request`** carrying a `RequestDetail` `{id, ref, column, raw?, signal?, deliver}` — **`deliver` is required**, and a detail without a function one is rejected outright; `<hdml-io>` announces **`hdml-io-ready`** when it can receive (the symmetric handshake, de-duped by `id`) and **`hdml-io-gone`** at disconnect (the generation space has ended). Delivery is **callback-only**: [`Delivery`](src/hdio/delivery.ts) is the consumer-facing union (`data` / `absent` / `error`, each with a `DeliveryCode` where it can fail), re-exported from [`HdmlIo.ts`](src/hdio/HdmlIo.ts) for external consumers and imported **type-only** from `./delivery` in-repo. Consumers adopt by the **stamp** (`generation >= latest`), not the kind. See [docs/hdio-client.md](docs/hdio-client.md#the-discovery-bus--subscription-registry-step-08-d7d8).
- **HDIO HTTP client** — `<hdml-io host tenant token>` targets the post-006 tenant routes at one base (`host`). There is **no** `sessions` bootstrap: in token mode the `token` attribute is a single-use **handoff code** that `HdioClient` redeems at `POST {host}/{tenant}/api/v1/auth/token` `{token}` for the `{access_token, refresh_token}` pair, held **in memory only** (silently refreshed via `POST …/auth/token/refresh`). It then `POST {host}/{tenant}/api/v1/documents/dynamic` with an `application/octet-stream` body of the `DocumentFilesStruct` FlatBuffers (the whole document, re-sent every change — no dedup) carrying a real `Authorization: Bearer <access>`; the **201** `{ stored[], ddl[] }` response is folded into the ref→key→stored registry. See [docs/hdio-client.md](docs/hdio-client.md).
- **Four entry points** — `.` (the compatibility root: 11 HDQL elements + `<hdml-io>`, exactly what it always registered), `./hdio`, `./hdql` and `./hdvl`, declared in an `exports` map. The three sub-entries are purely additive; `./hdvl` registers the 21 display tags. `exports` is a resolution **fence**, so deep paths like `@hdml/components/esm/hdql/HdmlFrame.js` no longer resolve — that break is intended. See [docs/integration.md](docs/integration.md#entry-points).
- **npm package shape** — `main: cjs/index.js`, `module: esm/index.js`, `types: dts/index.d.ts`, `customElements: custom-elements.json` (CEM, generated by `npm run manifest`), plus the `exports` map and a `sideEffects` array covering both module formats of all four entries; plus an unreferenced IIFE bundle at `bin/index.min.js`, built from `src/bundle.ts` and carrying all three layers. See [docs/integration.md](docs/integration.md).

## Conventions

- **No source comments unless they explain *why*.** TypeDoc `@tagname` / `@attribute` /
  `@event` JSDoc on the class is the public-facing reference — keep it accurate; CEM analysis
  reads it.
- **Attribute property keys are `*_ATTRS_LIST` enums**, not literals — e.g.
  `[CONN_ATTRS_LIST.NAME]: null | string = null` (see [src/hdql/HdmlConnection.ts:159](src/hdql/HdmlConnection.ts#L159)). The enum lives in `@hdml/types`; do not hardcode attribute strings here.
- **Display tag names and attribute keys come from [`src/hdvl/vocabulary.ts`](src/hdvl/vocabulary.ts)** — never a direct `@hdml/types` import in a display element file, and never a literal. That module is the only importer of the display vocabulary, so the 21 tags and 20 attribute enums are auditable in one place. (`src/hdql/` keeps importing its eight data enums directly, as it always has; and `@customElement("hdml-io")` stays a literal, because `HDML_TAG_NAMES` has no `IO` member — `hdml-io` is neither a data nor a display tag.) See [docs/decisions.md](docs/decisions.md).
- **All HDQL elements extend [`HdqlElement`](src/hdql/HdqlElement.ts#L8)**. Subclasses *do not* override the lifecycle hooks — the base hooks `connected`/`disconnected`/`attributeChanged` already dispatch `hdom-changed`. Subclasses only declare `@property` fields.
- **Worker code path:** `src/hdio/HdmlIo.worker.ts` exports `const _script = "_script"` as a build-time sentinel. The custom esbuild plugin in [.esbuildrc.mjs:8-45](.esbuildrc.mjs#L8-L45) bundles the worker and rewrites this constant to the bundled source string in the IIFE build only. In `esm/`/`cjs/` builds the sentinel survives, and `HdmlIo` falls back to running the message handler on the main thread (`globalThis.self`). See [docs/decisions.md](docs/decisions.md#why-_script).
- **Lint/format rule that bites:** `max-len: 70`, `printWidth: 70` (ESLint + Prettier). Wrap aggressively.
- **TypeDoc output is isolated under `docs/api/`.** `npm run docs` writes generated HTML to `./docs/api` and `npm run clear` removes only `docs/api` — so the hand-written agent docs (`docs/*.md`) survive a `clear`/`build`. The [.gitignore](.gitignore) ignores `docs/*` and re-includes `!docs/*.md`, so `docs/api/` stays untracked while the `.md` are committed. (Previously `clear` did `rm -rf docs`, deleting the tracked `.md` from the working tree; that TODO is now resolved.)
- **Tests use TDD-style globals.** `.testrc.js` sets `ui: "tdd"` — write `suite` / `test`, not `describe` / `it`. See an example at [src/hdql/HdmlConnection.test.ts:11](src/hdql/HdmlConnection.test.ts#L11).
- **Two export conditions.** `MODE=prod` selects the `prod` package export condition (both dev server and test runner); the default uses `development`. `TODO(confirm: which @hdml/* package actually publishes both conditions and what the dev one swaps in.)`
- **License header.** Every TS source carries the four-line `@author / @copyright / @license Apache-2.0` JSDoc preamble. Preserve it.
